## FedAvg 공개 코드 파악

### 각 소스 코드 파일의 역할
| 파일 | 역할 |
|---|---|
| `models.py` | 신경망 모델의 아키텍처(구조)를 정의합니다. 다층 퍼셉트론(MLP)과 MNIST, Fashion-MNIST, CIFAR 데이터를 위한 합성곱 신경망(CNN) 클래스들이 포함되어 있습니다. |
| `options.py` | 학습에 필요한 하이퍼파라미터(에폭, 클라이언트 수, 참여 비율, 학습률 등)를 터미널 명령어로 입력받을 수 있도록 설정하는 파일입니다. |
| `sampling.py` | 전체 데이터셋을 여러 클라이언트에게 어떻게 나누어 줄지 분할 방식을 정의합니다. 데이터 분포를 균등하게 나누는 IID 방식과 편향되게 나누는 Non-IID 방식의 샘플링 함수가 포함되어 있습니다. |
| `update.py` | 개별 클라이언트가 서버로부터 받은 모델을 자신의 로컬 데이터로 학습시키는 `LocalUpdate` 클래스와, 학습 후 글로벌 모델의 성능을 평가하는 `test_inference` 함수가 구현되어 있습니다. |
| `utils.py` | 데이터를 불러와 샘플링 함수와 연결하는 `get_dataset` 함수와, 서버가 클라이언트들의 가중치를 모아 평균을 내는 연합학습의 핵심 로직인 `average_weights` 함수를 포함합니다. |
| `baseline_main.py` | 연합학습을 사용하지 않고, 모든 데이터를 중앙 서버에 모아서 한 번에 학습시키는 전통적인 머신러닝 방식(Baseline)의 실행 파일입니다. |
| `federated_main.py` | 연합학습을 실제로 동작시키는 메인 실행 파일입니다. 글로벌 모델 초기화, 매 라운드마다 클라이언트 선택, 로컬 업데이트 지시, 글로벌 가중치 갱신 및 결과 저장 과정을 총괄합니다. |

**코드 매칭**: `options.py`의 `--epochs` 인자에 해당합니다. (원본 코드 작성자가 변수명을 round 대신 epochs로 지어두어서 매우 헷갈리기 쉽습니다.) `federated_main.py`의 가장 바깥쪽 학습 반복문이 바로 이 글로벌 라운드 횟수만큼 돌아가게 됩니다.

→ 다시 말해, option에 있는 epoch는 round임, 실제 개별 클라이언트의 epoch는 `--local_ep`에 해당

- **모델**: "모델과 학습 설정을 팀이 선정"이라고 되어있음 (모델과 하이퍼파라미터는 직접 건드리는 것)
  - 근데 기본 옵션 값인 MLP 모델로 하면
  - MLP의 한계: MLP는 2차원 이미지를 1차원으로 길게 펴서(Flatten) 입력받기 때문에, 이미지 픽셀 간의 상하좌우 공간적 연관성을 모두 잃어버리게 되어 정확도가 매우 낮게 나옵니다. 정상 환경에서의 베이스라인 성능이 낮으면, 명세서에서 요구하는 '공격 피해'나 '방어 효과'에 따른 성능 변화를 유의미하게 분석하기 어렵습니다. 이와 같은 한계점을 가지게 된다
  - → 따라서 CNN 사용 (또한, 이미지에 한해 CNN이 속도가 더욱 빠르다)
- **데이터셋**: 명세서에 주어진 cifar 사용해야 함 (기본이 mnist로 되어 있음)
- **epoch**(정확히는 round임): 10번이 default이지만 그냥 적어놓음
- **iid 1**
  - `--iid 1`: IID 환경 (데이터가 모든 클라이언트에게 균등하게 분할됨)
  - `--iid 0`: Non-IID 환경 (특정 클라이언트에 특정 클래스 데이터가 쏠림)
- **gpu 0**을 해야 gpu를 사용해서 할 수 있음
- 추가로 **seed**는 건드리지 않으면 default 1로 고정되어 있음 (seed가 고정되어있기 때문에 같은 값이 나옴 코드만 같으면)

(원문 문서의 실행 화면 참고)

결과는 위와 같이 나옴. 이 수치가 아무런 조작이 없는 '정상 환경에서의 최종 테스트 정확도' 기준점이 되며, 앞으로 내부자 협력 공격이나 방어 기법을 적용했을 때 이 45.97%라는 기준에서 얼마나 피해를 입고 복구되는지(공격 피해, 방어 개선 수치)를 계산하여 %p로 분석하게 된다.

참고로 위의 코드는 현재 `--num_users`와 `--frac`을 10과 1.0로 설정되어 있지 않음. num users 100으로 하고 frac을 0.1로 하여 10명을 맞춘 것이므로 다름.
(똑같이 10명이 학습하지만 각 클라이언트가 학습해야 할 데이터양이 500장(user 100, frac 0.1)과 5000장(user 10, frac 1.0)으로 차이가 남)

### 실험2
(원문 문서의 실행 화면 참고)

이 코드는 `--num_users`와 `--frac`을 10과 1.0로 설정하고 한 코드
(그러나 시간이 오래 걸리기 때문에 epoch 2, local ep을 1로 하여 돌렸다.)

(원문 문서의 실행 화면 참고)

그때의 결과. user 100, frac 0.1보다 시간은 두배나 걸렸음에도 불구하고 epoch와 local ep을 낮춘 탓인지 전반적인 acc가 낮게 나왔다.

- **현재 상황**: 1명당 5,000장의 이미지를 가졌는데 한 번에 10장씩만 GPU에 올립니다. 즉, 1에폭을 돌기 위해 GPU가 자잘하게 500번이나 연산을 쪼개서 수행해야 하므로 엄청난 병목(오버헤드)이 발생하여 1398초나 걸린 것입니다.
- **해결책**: 한 번에 학습하는 묶음인 배치 사이즈(`--local_bs`)를 64 또는 128로 대폭 늘려야 합니다. 이렇게 하면 GPU가 한 번에 많은 데이터를 쫙 빨아들여 병렬로 연산하므로 속도가 비약적으로 빨라집니다.

**해결 방안**: 연합학습에서 성능을 올리려면 글로벌 라운드(서버와 통신)가 어느 정도 확보되어야 합니다. 다음 설정을 기준으로 팀원들과 테스트해 보시길 권장합니다.
- 배치 사이즈 (`--local_bs`): 64 (무조건 늘려야 속도가 빨라집니다)
- 글로벌 라운드 (`--epochs`): 20 ~ 30 (통신을 여러 번 해야 성능이 올라가고, 나중에 방어 기법의 추이를 그래프로 관찰하기 좋습니다)
- 로컬 에폭 (`--local_ep`): 3 ~ 5 (한 번 통신할 때마다 클라이언트가 혼자 너무 오래 학습하면 모델이 망가질 수 있으므로 적당히 설정합니다)

### 실험3
(원문 문서의 실행 화면 참고)

수정된 코드: Epoch(라운드)를 20으로, local ep 3, local bs(batch size)를 64로 함

(원문 문서의 실행 화면 참고)

결과: 시간도 적게 걸리고 acc도 아까보다 높게 나옴

- **배치 사이즈 128 변경**: 늘리셔도 전혀 문제없습니다. Kaggle의 GPU(T4, 16GB VRAM)는 `--local_bs 128`을 넉넉하게 감당합니다. 64에서 128로 올리면 1에폭당 쪼개는 횟수가 더 줄어들어 속도가 조금 더 빨라지며, 모델 성능에도 악영향을 주지 않는 안전한 수치입니다.
- **에폭 vs 로컬 에폭** (성능 향상을 위한 선택):
  - 글로벌 라운드(`--epochs`) 증가 (추천): 시간이 여유롭다면 `--epochs`를 30~50 정도로 늘리는 것이 정확도를 올리는 가장 확실한 방법입니다. 50라운드를 돌려도 약 40분 정도면 완료될 것입니다.
  - 로컬 에폭(`--local_ep`) 유지: 로컬 에폭은 3~5 정도로 유지하는 것이 좋습니다. 클라이언트가 서버와 통신하지 않고 로컬에서 너무 오래 학습(예: 10 이상)하면, 각자의 데이터에 과적합되어 나중에 서버에서 가중치를 합칠 때 오히려 성능이 떨어지는 '클라이언트 드리프트(Client Drift)' 현상이 발생합니다.
- **옵티마이저 및 학습률 (lr)**: 현재의 sgd와 `--lr 0.01`을 그대로 고정하는 것을 권장합니다. 연합학습(FedAvg) 구조에서 가장 안정적으로 수렴하는 표준 설정입니다. adam은 로컬에서는 빠르지만 글로벌 합산 시 가중치가 튀어 불안정해질 위험이 있습니다.
  - → adam으로 해보고 성능 비교해보기

시험해볼 현재 코드:
```
!cd Federated-Learning-PyTorch/src && python federated_main.py --dataset cifar --model cnn --epochs 40 --local_ep 3 --local_bs 128 --num_users 10 --frac 1.0 --iid 1 --gpu 0
```

**local epoch가 3이면 너무 적은거 아닌가?**

1. local_ep가 3이어도 충분한 이유
   - 충분한 총 학습량: epochs = 40, local_ep = 3 설정이면 각 클라이언트는 통신을 주고받으며 모델을 총 120 에폭(40 (원문 수식 생략) 3) 학습하게 됩니다. 딥러닝 모델이 데이터를 복습하기에 결코 적은 횟수가 아닙니다.
   - 실증된 정확도: 방금 진행한 20라운드 실험만으로도 53.50%라는 훌륭한 정상 성능(Baseline)을 확보했습니다.
2. local_ep를 5 이상으로 올릴 때 발생하는 문제점
   - 클라이언트 편향 (Client Drift) 현상: 연합학습에서 클라이언트가 서버와 가중치를 섞지 않고 혼자 오래 학습(local_ep 증가)할수록, 모델이 전체 데이터가 아닌 '자기 로컬 데이터'에만 과적합(Overfitting)됩니다. 이 상태로 서버에서 가중치를 평균 내면 오히려 모델 성능이 흔들리거나 떨어질 수 있습니다.
   - Non-IID 환경에서의 성능 폭락: 특히 명세서 4단계의 Non-IID(레이블 편향) 실험을 할 때 local_ep가 너무 높으면 각 클라이언트가 특정 숫자/클래스에만 극단적으로 치우쳐 학습되기 때문에, 서버 집계 후 정확도가 급격히 떨어지는 현상이 심해집니다.
   - 실험 효율성 하락: 과제 특상 4단계에서 정상/공격/방어/지연/Non-IID 등 수많은 조건의 비교 실험을 반복해야 합니다. local_ep를 늘려 라운드당 시간을 늘리는 것보다, local_ep = 3으로 연산 시간을 아끼고 글로벌 라운드(epochs)를 확보하여 실험을 빠르게 돌리는 것이 훨씬 유리합니다.

### 실험4
(원문 문서의 실행 화면 참고)

수정된 코드: Epoch(라운드)를 40으로, local ep 3, local bs(batch size)를 128로 함

(원문 문서의 실행 화면 참고)

결과: 실험 3보다도 시간은 2배나 걸렸지만 acc는 오히려 감소함. 그 이유는 크게 두 가지 기술적 요인 때문입니다.
- **배치 사이즈에 따른 업데이트 횟수와 노이즈 차이**: 클라이언트가 5,000장의 데이터를 가졌을 때, 배치 사이즈 128은 1에폭당 약 39번 가중치를 업데이트하지만, 64는 약 78번 업데이트합니다. 배치 사이즈가 작을수록 학습 과정에서 미세한 떨림(노이즈)이 더 많이 발생하는데, 이 떨림이 오히려 모델이 특정 데이터에 갇히지 않고 더 나은 최적점을 찾아가게 돕는 '정규화(Regularization) 효과'를 주어 테스트 정확도가 더 높게 나오는 경우가 많습니다.
- **연합학습(FedAvg)의 진동(Oscillation) 특성**: 연합학습의 정확도는 직선으로 상승하지 않고 출렁이며 올라갑니다. 20라운드 시점이 우연히 성능 진동의 '고점'이었고, 40라운드는 가중치가 다시 조정되는 과정의 '저점'이었을 수 있습니다. 또한, 고정된 학습률(lr=0.01)을 40라운드 내내 줄이지 않고 그대로 유지하면, 모델이 정답에 다가갔다가도 다시 튕겨 나가는 현상이 발생합니다.

이 프로젝트의 목적은 '절대적으로 가장 높은 정확도'를 찾는 것이 아니라, 공격을 받았을 때 정확도가 얼마나 떨어지는지 비교할 '안정적인 비교 기준점'을 세우는 것입니다.

시간도 1014.14초(약 17분)로 짧고 성능도 53.50%로 잘 나온 20라운드, 로컬 에폭 3, 배치 사이즈 64 설정을 팀의 최종 베이스라인으로 확정하시는 것을 강력히 추천합니다. 라고 함.

### 단계적 변인 통제(Sequential Variable Control) 및 탐색 순서의 타당성
**단계적 변인 통제 및 탐색 순서의 논리적·수학적 근거**

본 실험은 6종의 핵심 하이퍼파라미터 조합 공간(총 (원문 수식 생략)가지 경우의 수)을 전수 탐색할 때 발생하는 연산 비용 폭발을 방지하고 각 변인의 독립적 기여도를 규명하기 위해, 모델 표현력 검증 (원문 수식 생략) 최적화 경로 안정화 (원문 수식 생략) 통신·연산 주기 확정 (원문 수식 생략) 수렴 환경에서의 배치 효율 검증으로 이어지는 6단계 순차 탐색 전략을 채택하였다.

1. **1단계: 공간적 귀납 편향(Inductive Bias) 선행 검증 (model 결정)**
   최적화 알고리즘이나 학습 주기를 조정하기 전, 입력 데이터의 구조적 특징을 수용할 수 있는 기반 모델의 표현력을 최우선으로 검증해야 한다. 1차원 평탄화(Flatten)로 인해 픽셀 간 공간 정보를 소실하는 MLP와 국소 수용 영역을 보존하는 CNN의 특징 추출 능력을 선제적으로 비교하여, 과소적합(Underfitting)이 배제된 기준 아키텍처를 고정하였다.
2. **2·3단계: 파라미터 공간의 수렴 안정성 및 보폭 확보 (optimizer (원문 수식 생략) lr 순차 결정)**
   모델 구조가 확정된 후에는 손실 함수 (원문 수식 생략)의 최소점을 탐색하는 최적화 알고리즘과 학습 보폭(원문 수식 생략)을 순차적으로 결정한다. 특히 중앙 서버가 다수 클라이언트의 가중치를 선형 평균하는 FedAvg 구조에서는 적응형 모멘텀을 사용하는 Adam이 로컬 데이터 분포 차이에 의해 집계 시 발산할 위험이 존재한다. 따라서 알고리즘(SGD vs Adam)의 수렴 안정성을 먼저 판별한 뒤, 해당 알고리즘에 최적화된 학습률을 정밀 탐색하여 라운드당 가중치 갱신의 기준 보폭을 확립하였다.
3. **4단계: 총 연산 예산 대비 수렴 포화점 탐색 (epochs 결정)**
   안정적인 모델과 학습률이 확보된 상태에서 전체 글로벌 라운드(원문 수식 생략)를 확장하며 테스트 정확도가 수렴 포화 구간에 진입하는 시점을 탐색한다. 이는 후속 4단계의 다중 시드 및 공격·방어 교차 실험(총 20회 이상 반복)을 제한된 GPU 자원 내에서 완수할 수 있는 총 통신 라운드 예산을 확정하기 위함이다.
4. **5단계: 로컬-글로벌 편향 균형 조절 (local_ep 결정)**
   전체 통신 라운드(원문 수식 생략)가 고정된 상태에서 단일 라운드 내 로컬 반복 횟수(원문 수식 생략)를 조절한다. (원문 수식 생략)가 과도할 경우 각 클라이언트가 로컬 손실 최소점 (원문 수식 생략)로 과적합되어 글로벌 최적점과 괴리가 커지는 클라이언트 편향(Client Drift, (원문 수식 생략))이 발생하며, 반대로 너무 작으면 통신 대비 수렴 속도가 저하되므로 두 요인의 균형점을 도출하였다.
5. **6단계: 수렴 구간에서의 배치 크기별 성능·시간 트레이드오프 최종 검증 (local_bs 후순위 결정)**
   로컬 배치 크기(원문 수식 생략)는 1 에폭당 가중치 업데이트 횟수($I = \lceil N/B \rceil$)를 직접 변화시킨다. 만약 라운드가 적은 초기 단계에서 배치 크기를 먼저 비교할 경우, 업데이트 빈도가 6배 이상 많은 작은 배치(원문 수식 생략)가 초반 수렴 속도 우위로 인해 과대평가되는 편향이 발생한다. 따라서 앞선 1~5단계를 통해 모든 후보군이 충분히 수렴할 수 있는 글로벌 라운드와 학습률을 먼저 확정한 뒤, 마지막 단계에서 배치 크기별 최종 일반화 정확도와 실제 GPU 소요 시간 간의 공학적 최적점(Pareto Optimal)을 공정하게 판별하였다.

### 평가 지표 분리
본 실험의 1단계(기본 모델 및 하이퍼파라미터 선정)에서는 명세서의 전체 평가지표 중 전역 테스트 정확도(Global Test Accuracy), 전역 손실(Loss), 과적합 갭(Train-Test Gap), 그리고 총 실행 시간(Total Run Time)만을 핵심 지표로 채택하였으며, 클래스별 정밀도·재현율 및 클라이언트별 개별 성능 측정은 후속 4단계(운영 환경 및 공격·방어 비교 실험)로 분리하여 적용하였다. 이러한 지표 분리의 타당성은 다음과 같다.

기준 환경(Baseline) 탐색 단계에서는 모든 클라이언트가 전체 10개 클래스의 데이터를 동일한 표본 수와 균등한 확률 분포로 배정받는 IID(Independent and Identically Distributed) 조건을 적용한다. 이 상태에서는 클라이언트 (원문 수식 생략)의 로컬 데이터 분포 (원문 수식 생략)가 전체 데이터 분포 (원문 수식 생략)와 통계적으로 동일하므로, 클라이언트 간 성능 편차나 특정 클래스에 대한 편향적 성능 저하가 발생하지 않는다. 따라서 전역 평균 지표만으로도 모델의 수렴 상태와 일반화 성능을 충분히 대표할 수 있다.

### 초기 탐색용 통제 변인(Control Variables) 설정 근거
**탐색 단계별 임시 고정값 설정 기준**

1~5단계 순차 탐색 과정에서 아직 결정되지 않은 후순위 하이퍼파라미터가 실험 결과의 왜곡이나 연산 병목을 유발하지 않도록, 아래와 같은 기준에 따라 임시 고정값을 설정하였다.

| 항목 | 설정 근거 |
|---|---|
| 임시 로컬 배치 크기 (`--local_bs 64`) | 오픈소스 기본값(10)은 GPU 병렬 처리 효율 저하로 인해 10라운드 기준 약 18분 40초(1,120초)가 소요되어 다단계 탐색의 물리적 병목을 유발하며, 128은 업데이트 빈도 부족으로 초기 수렴이 지연된다. 따라서 연산 속도와 미니배치 정규화 효과가 균형을 이루는 64를 1~5단계 탐색용 기준 배치 크기로 고정하였다. |
| 임시 글로벌 라운드 (`--epochs 10`) | 1~3단계(모델, 옵티마이저, 학습률)의 목적은 최종 포화 정확도 달성이 아니라 설정 간 초기 수렴 기울기(원문 수식 생략)와 발산 여부의 상대적 우열을 판별하는 것이다. 10라운드만으로도 각 변인의 수렴 경향성을 명확히 대조할 수 있으므로 불필요한 GPU 연산 낭비를 막기 위해 탐색 라운드를 10으로 통제하였다. |
| 임시 로컬 에폭 (`--local_ep 3`) | 오픈소스 기본값(10)은 단일 라운드 내 과도한 로컬 학습으로 클라이언트 편향을 유발할 수 있고, 1은 통신당 학습량이 부족하므로 그 중간값인 3을 초기 기준값으로 채택하였다. |
| 임시 학습률 (`--lr 0.01` / `0.001`) | 1·2단계 탐색 시 SGD에는 표준 보수적 보폭인 0.01을, 적응형 학습률을 사용하는 Adam에는 발산 방지를 위한 표준 기본값 0.001을 적용하여 알고리즘 자체의 순수 수렴 특성을 공정하게 비교하였다. |
| 시뮬레이션 환경 통제 인자 (`--num_users 10 --frac 1.0 --iid 1 --seed 1`) | 프로젝트 명세서 1단계 기준에 따라 클라이언트 10명 전원 참여, 균등 데이터 분포(IID)로 정상 환경을 고정하고 난수 시드를 통일하여 실험의 통계적 재현성을 확보하였다. |

### 실험 결과의 심층 원인 분석 ("왜 SGD가 아닌 Adam이 더 좋게 나왔는가?")
**[2단계 분석: 적응형 모멘텀 기반 파라미터 공간 탐색과 FedAvg 수렴 가속화]**

1) **1차·2차 모멘트 추정을 통한 초기 수렴 속도 극대화**
기존에 보편적으로 사용되는 SGD는 모든 파라미터에 동일한 스칼라 학습률(원문 수식 생략)을 적용하므로, 곡률이 가파른 방향에서는 진동하고 완만한 평탄면(Saddle Point)에서는 보폭이 극도로 느려지는 한계가 있다. 이로 인해 Round 1 테스트 정확도가 12.17%(무작위 추측 수준)에 머물렀으며, 10라운드가 종료된 시점에도 41.31%에 그쳤다. 반면 Adam은 기울기의 1차 모멘트(Momentum)와 2차 모멘트(분산 기반 적응형 스케일링)를 동시에 추정하여 파라미터별로 최적화된 보폭을 동적 할당한다. 그 결과 Round 1에서부터 이미 34.48%에 도달하며 SGD의 7라운드 수준 성능을 단 1라운드 만에 달성하였고, 이후에도 발산 없이 매 라운드 단조 증가(Monotonic Increase)하여 56.88%를 기록하였다.

2) **취약 클래스(Hard Classes) 분류 성능의 비약적 개선**
클래스별 상세 지표를 비교하면 Adam의 표현력 확보 효과가 더욱 뚜렷하게 드러난다. SGD 환경에서는 시각적 변별이 까다로운 동물 클래스인 bird(F1 0.1544, Recall 0.1000)와 cat(F1 0.2372, Recall 0.2040)에서 심각한 미분류 현상이 발생하였다. 그러나 Adam 적용 시 bird의 F1-Score는 0.4447(+0.2903), cat은 0.4113(+0.1741)으로 대폭 상승하였으며, 전 10개 클래스 모두 F1-Score 0.41 이상의 균형 잡힌 분류 성능을 확보하여 Macro F1-Score가 0.3947 (원문 수식 생략) 0.5663으로 급상승하였다.

3) **FedAvg 집계 과정에서의 수렴 안정성 검증**
이론적으로 클라이언트 간 데이터 분포가 극단적으로 편향(Non-IID)된 환경에서는 Adam의 로컬 모멘텀 상태가 서버 집계 시 충돌을 일으킬 우려가 제기되나, 본 실험의 기준 환경(IID 균등 분포)에서는 각 클라이언트의 손실 지형(Loss Landscape)이 유사하여 모멘텀 방향이 일관되게 정렬되었다. 또한 매 라운드 순수 학습 소요 시간 역시 SGD(라운드당 평균 37.56초)와 Adam(라운드당 평균 38.37초) 간 차이가 1초 미만으로 연산 오버헤드가 사실상 존재하지 않았다.

### 추가: 옵티마이저별 기준 학습률 차등 설정 근거 (SGD: 0.01 vs Adam: 0.001)
> "옵티마이저를 비교하는건데 학습률이 같아야 하는거 아니야??"라는 질문에 대한 답

**옵티마이저별 가중치 갱신 메커니즘 차이에 따른 공정 비교 기준 수립**

본 2단계 실험에서는 SGD와 Adam의 알고리즘적 수렴 특성을 공정하게 비교하기 위해, 두 옵티마이저에 동일한 스칼라 학습률을 강제하지 않고 각 알고리즘의 표준 기준 보폭인 SGD: lr=0.01과 Adam: lr=0.001을 적용하였다. 이는 다음과 같은 수학적·공학적 근거에 기반한다.

1. **가중치 업데이트 스케일(Update Scale)의 구조적 차이**
   - SGD는 계산된 기울기(원문 수식 생략)에 학습률(원문 수식 생략)을 직접 곱해 가중치를 갱신(원문 수식 생략)하므로, 초기 기울기 크기가 작아질수록 보폭도 함께 줄어든다. 따라서 의미 있는 학습 진전을 위해서는 상대적으로 큰 보폭(원문 수식 생략)이 요구된다.
   - 반면 Adam은 1차 모멘트(원문 수식 생략)를 2차 모멘트의 제곱근(원문 수식 생략)으로 나누어 기울기를 정규화(Normalization)한 뒤 업데이트(원문 수식 생략)한다. 이로 인해 기울기 크기와 무관하게 매 스텝 약 (원문 수식 생략) 수준의 일관된 보폭으로 이동하므로, SGD와 동일한 0.01을 적용할 경우 매 스텝 가중치가 과도하게 진동하여 손실 함수가 발산(Divergence)하게 된다.
2. **표준 기본값(Default Baseline) 기반의 공정성 확보**
   - PyTorch 공식 프레임워크 및 본 프로젝트의 코드베이스(`options.py`)에서 채택한 SGD의 표준 기본값은 0.01이며, 원 논문(Kingma & Ba, 2015) 및 PyTorch `torch.optim.Adam`의 공식 표준 기본값은 0.001이다.
   - 각 알고리즘이 본래 의도된 정상 작동 범위(Nominal Operating Regime) 내에서 발휘하는 최적의 기본 수렴 성능을 먼저 대조한 뒤, 후속 3단계(학습률 정밀 탐색)에서 채택된 옵티마이저의 보폭을 세밀하게 튜닝함으로써 실험의 논리적 엄밀성을 확보하였다.

### 실험 결과의 심층 원인 분석 ("왜 0.005가 아닌 0.001을 선택해야 하는가?")
**[3단계 분석: 수렴 속도-안정성 트레이드오프 및 오버슈팅(Overshooting) 방지]**

1) **과소 보폭(lr=0.0005)의 수렴 지연**
학습률을 0.0005로 축소할 경우, 매 로컬 스텝의 파라미터 갱신 폭이 지나치게 작아 제한된 10라운드 내에 손실 함수의 최적 영역에 도달하지 못하는 수렴 지연 현상을 보였다. 그 결과 최종 테스트 정확도가 51.94%에 머물렀으며, 기준값(0.001, 56.88%) 대비 -4.94%p 낮은 성능을 기록하였다.

2) **과대 보폭(lr=0.005)의 초기 불안정 및 손실 반등(Overshooting) 징후**
학습률을 0.005로 상향한 경우, FedAvg의 가중치 평균화 효과가 개별 클라이언트의 기울기 진동을 일부 상쇄하면서 10라운드 시점의 단순 테스트 정확도는 58.44%로 가장 높게 나타났다. 그러나 라운드별 세부 수렴 궤적을 분석한 결과 두 가지 명백한 불안정 징후가 확인되었다.
- 첫째, 초기 탐색 불안정성: Round 1에서 보폭이 과도하게 커 최적 경로를 이탈하면서 테스트 정확도가 18.79%에 그쳐, 0.001(34.48%) 대비 초기 수렴이 크게 흔들렸다.
- 둘째, 손실 함수 반등(Overshooting): Round 9(Test Loss: 96.2115)에서 Round 10(Test Loss: 97.0965)으로 전환될 때 테스트 손실값이 다시 상승하는 진동 현상이 시작되었다. 이는 학습 보폭이 손실 골짜기(Local Minimum)의 최저점에 안착하지 못하고 주변을 튕겨 다니기 시작했음을 의미한다.

3) **장기 라운드 확장 및 비균등(Non-IID)·공격 환경에서의 수렴 안정성 확보**
반면 기준 학습률 lr=0.001은 Round 1부터 34.48%라는 가장 높은 초기 정확도로 출발하여, Round 10까지 Test Loss가 142.78에서 96.0507(3개 후보 중 최저치)로 단 한 번의 반등 없이 매끄럽게 단조 감소(Monotonic Decrease)하였다. 후속 4단계(글로벌 라운드 확장) 및 본 실험의 악조건(Non-IID 데이터 편향, Byzantine 악성 공격 등)에서는 가중치 충돌이 증폭되므로, 단기적인 1.56%p의 정확도 우위보다 손실 함수가 발산하지 않고 끝까지 파고들 수 있는 수렴 안정성을 확보하는 것이 공학적으로 훨씬 타당하다.

### 최종 선정 결론 및 다음 단계 안내
- **3단계 확정값**: `--lr 0.001`
- **선정 요약**: lr=0.005는 10라운드 단기 정확도(58.44%)는 소폭 높았으나 초기 수렴 불안정과 Round 10에서의 Test Loss 반등(96.21 (원문 수식 생략) 97.10)이라는 오버슈팅 징후가 관측되었다. 반면 lr=0.001은 최저 테스트 손실(96.0507)과 전 구간 단조 감소하는 최상의 수렴 안정성을 입증하였으므로, 후속 다중 라운드 확장 및 악조건 환경 실험의 안정적 기반 확보를 위해 lr=0.001을 최종 학습률로 확정한다.

- **선정 요약**: local_bs=32는 후반부 로컬 과적합으로 인한 손실 상승(100.9062)을, local_bs=128은 업데이트 횟수 부족으로 인한 정확도 저하(56.99%)를 보인 반면, local_bs=64는 최고 테스트 정확도(60.32%)와 최저 테스트 손실(92.4249)을 달성하였으므로 최적 로컬 배치 크기로 최종 확정한다.

이제 확정된 기준선(`--model cnn --optimizer adam --lr 0.001 --epochs 20 --local_ep 3 --local_bs 64 --num_users 10`)을 고정한 상태로 프로젝트 핵심 실험(정상 환경 vs 지연/부분참여 vs Non-IID 데이터 편향)으로 넘어갈 준비가 완료된다.

## 정리
1단계부터 6단계까지 각 기준값이 확정된 핵심 과정은 다음과 같습니다.

| 단계 | 확정값 | 근거 |
|---|---|---|
| 1. 모델 아키텍처 | `--model cnn` | CIFAR-10 컬러 이미지의 공간적 패턴을 보존하며 특징을 추출하는 CNN이 평탄화 과정에서 구조가 손실되는 MLP(43.25%)를 +13.63%p 격차로 압도하여 채택되었습니다. |
| 2. 옵티마이저 | `--optimizer adam` | 분산 환경의 기울기 진동을 보정하고 파라미터별 적응형 학습률을 제공하는 Adam이 고정 보폭 방식의 SGD(39.75%)보다 +17.13%p 높은 정확도와 빠른 초기 수렴을 보여 선정되었습니다. |
| 3. 학습률 | `--lr 0.001` | 0.005는 10라운드 단기 정확도는 소폭 높았으나 후반부 테스트 손실이 반등하는 오버슈팅(Overshooting) 징후가 나타났고, 0.0005는 수렴이 지연되었습니다. 전 구간 손실이 단조 감소하며 가장 안정적인 수렴 곡선을 그린 0.001을 최종 채택했습니다. |
| 4. 글로벌 라운드 | `--epochs 20` | 10라운드에서 20라운드로 확장 시 정확도가 60.32%까지 상승하고 손실이 최저점(92.42)을 기록한 반면, 40라운드에서는 과적합으로 손실이 111.85까지 폭증하여 연산 효율과 일반화 성능의 최적 포화점인 20을 확정했습니다. |
| 5. 로컬 에폭 | `--local_ep 3` | 1회는 로컬 학습량 부족(53.59%)으로 수렴이 느렸고, 5회는 클라이언트가 각자 데이터에만 치우치는 클라이언트 드리프트(Client Drift)로 인해 손실이 130.81까지 악화되어, 통신과 연산의 최적 균형점인 3을 선택했습니다. |
| 6. 로컬 배치 크기 | `--local_bs 64` | 32는 잦은 스텝 누적으로 후반부 과적합을 유발했고, 128은 업데이트 횟수 부족(56.99%)을 보인 반면, 기울기 분산과 갱신 빈도의 균형을 맞춘 64가 최고 정확도(60.32%)와 최저 손실(92.42)을 기록하며 최종 확정되었습니다. |
